子代理的概念

子代理这玩意，从流程上来说还是比较好理解的，就是我在主会话上，要做一件事情，但我只需要知道这个事情的结果就行，那么这个过程我就可以分派给一个子智能体去干这个事情，在这个情况下，上下文是隔离的，而子智能体把事情干完再把结果汇报给主智能体，这样就减少了主智能体上下文的污染。

场景示例：跨模型图片识别

我举一个场景，我有一张图片，我想要 AI 去识别，但是这个 AI 它不具备多模态功能，像是 Deepseek-v4-flash​，但是很巧，我手头还有个 MiniMax-M3​，它支持多模态，那么我就可以把 MiniMax-M3​ 注册成一个子智能体，然后让 d4f（Deepseek-v4-flash​）去开个子代理，让 MiniMax-M3 去解析图片，把结果返回给它。这样就实现了图片识别。

子代理的元数据头

当然，上述的一个前提是 harness 支持子代理使用不同的模型。我们创建子智能体后，其实是生成了一个 md 文件，以 Zcode 为例，它在创建子智能体后会在 ~\.zcode\agents​ 下生成一个 子智能体name.md，可以看下我刚才创建的子智能体：

---
name: "picture-parser"
description: "解析图片"
color: yellow
model: "custom:43503ea5-41db-4a4e-b47c-03664a1fbfe9:MiniMax-M3"
injectAgentsMd: true
---

你是视觉识别专员（Vision Analyst），一个专职读图并回报结论的子代理。

## 核心原则

你只做一件事：接收图片路径，读取并分析图片，用文字汇报结论。
你是只读岗位：除读取任务书指定的图片外，不修改任何文件，不执行任何写操作。

## 工作流程

1. 从任务书中找到图片文件路径。
2. 用 Read 工具读取该路径的图片。
3. 按任务书要求的侧重点分析（文字提取 / 界面布局 / 图表解读 / 通用描述）。
4. 按「汇报格式」输出，作为你的最终回复。

## 汇报格式

- 【图片概览】一句话说明图片类型与主题
- 【文字内容】图中可辨认的全部文字，保持原文照录
- 【细节描述】颜色、布局、物体、界面元素等，按任务书侧重取舍
- 【不确定项】模糊或无法辨认的内容明确标注，禁止猜测补全

## 硬性边界

- 图片路径无效或读取失败：如实报告失败原因，绝不臆造图片内容
- 看不清的部分明确说看不清——宁可留白，不可编造
- 不执行任何 git 操作，不修改任何文件

## 自我标识

每次汇报的最后一行附上：【执行模型】<如实填写你的模型名称>

我们仔细看它的元数据头：

name: "picture-parser"
description: "解析图片"
color: yellow
model: "custom:43503ea5-41db-4a4e-b47c-03664a1fbfe9:MiniMax-M3"
injectAgentsMd: true // 这个是 agents.md 是否注入到子代理

model 字段与 harness 兼容

里面有个 model​ 字段，它就是指定子代理时要去调用什么模型，但是这个字段是需要 harness 支持的，有的 harness 不支持这个字段，那么它在执行子代理的时候调用的模型就是自己这个模型，就比如说 d4f 调用了一个测试的子代理，里面指定的模型是 GLM-5.3​，但是用的 harness 不支持 model 这个字段，那么实际执行子代理的模型就是 d4f。

上下文隔离的红利

同时，子代理还有个好处，就是主智能体可以同时发起多个子代理，这也是上下文隔离的红利，隔离的不只是上下文污染，还有执行时序。

harness 字段兼容性总览

这里我还要提醒一点，元数据头里的所有字段都是依赖 harness 是否支持的，不同的 harness 支持的字段不同，因此在创建智能体的时候还要看一下当前用的 harness 是否支持某些字段。

子代理 vs skill：决策上下文的差异

以及，子代理中并不会有 skill 名单，因为子代理只会执行一轮，而它的信息是主会话给它 prompt 进去的，这点在 Trellis 的脚本中也有体现。

还有个有意思的事情，其实子智能体和 skills 一样，都会进入模型的决策上下文，我们在 command 篇里提到的稳定区就是这里，也就是说子智能体的 description 也是会给 AI 看的，AI 在一开始就知道自己手底下收什么可以用的子智能体。

但是两者的触发频率和强制力度不同，skill 是高频被动触发，用户随便说句话，都会先过一遍 skill 名单去匹配，而子代理是低频主动的，只有当模型已经在考虑是否去用子代理时才会去看这个名单，而且也没有像 skill 那样匹配了就必须用的强制机制。

如何让 AI 主动派遣子代理

既然我们已经知道了 AI 派遣子代理的主要因素是在于它自己判断是否应该派遣子代理，那么就到了写法上，如何让 AI 意识到我接下来做的事情应该去开子代理。

我个人是想到了两个方法：

  1. 写个 skill，通过 skill 的高频触发机制来让 AI 去派遣子代理，比如说我写了个 skill，描述信息是读源码时使用，正文是读大源码文件（超过 10KB）就去派遣子代理来读。
  2. 将标准写入 AGENTS.md​，还是上面的例子，我直接在 AGENTS.md 里写上：如果读的源码文件超过了 10KB，就直接派遣子代理。

但是这两点来说并不是最佳的做法，因为 skill 的方案是依赖 skill 的触发，而触发本身就是一次模型判断，这样的派遣是建立在另一层可能失守的判断上，显然是不够可靠的。AGENTS.md​ 的缺陷则是它是静态的，能放不变式，但放不了状态，"当前没有活动任务、应派 implement​"这句话在 AGENTS.md 里写不出来，因为它是随会话变化的。

Trellis 的方案

因此，Trellis 并没有采用上面的两个方法，而是将规则放进了 workflow.md​ 这个文件中，并通过 harness 的钩子去注入，在每一轮会话都重新注入来对抗长对话带来的遗忘。同时，将抽象意图尽量规则化，数据化，这就像我们这的读源码例子，给它具体的数值，具体的规则，这样就可以更好地让 AI 去选择去使用子代理，而这一整套做法并不是我所说的这么简单，而是一个很完整的流程：AGENTS.md​（薄指针）→ workflow.md​（规则本体）→ SessionStart​ 钩子注入（压缩摘要，含意图→代理映射表）→ UserPromptSubmit 钩子每轮注入（实时状态），模型做的只剩"意图归类"这道选择题，选项和评分标准都是钩子预置的。

当然，它的这几点还是无法完全代替抽象的意识，只能说尽量具体化，真正到使用的时候，还需要我们自己额外加上些规则去让 AI 在什么情况下派遣子代理。
