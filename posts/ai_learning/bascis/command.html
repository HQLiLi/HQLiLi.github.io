Command篇

2026/08/30AI学习

2026.8.30 20:37

在了解 skill 后，command 的理解就比较轻松了。

首先，command 从文件形态上来说跟 skill 没有区别，就是一个 md 文件。作为一个初学者，我认为可以简单地片面地认为 command 就是一个不会自动注入上下文的 skill。这点在下面会说明。

与 skill 的区别

command 跟 skill 第一个最明显的区别就是，command 没有硬性规定元数据头（frontmatter）根本不认 name​，这是因为 skill 主要是自动注入的，因此需要 description​ 去让 AI 匹配当前是否要让 harness 注入到上下文。而 command 必须我们手动用 /​ 打出指令来执行，否则一般情况下 AI 不会去调用它。当然头信息里的信息也不全是给人看的，比如 allowed-tools​（收窄这次执行的工具白名单）、model​（单次换模型）、skills​（自动挂载某 skill），这三个都是参数注入，而像 description 的话就是给人看的。

形式对比

那么这里就引申出来一个新的疑问，既然 command 和 skill 在本质上区别不大，那我如果在 skill 中加入了 去遵循 command.md​ 这样的内容，AI 就去让 harness 将 command.md 正文注入了上下文，这个算 command 吗？

这种做法从效果上来说是起到了和 command 类似的作用，但是从形式上来说，完全不同，command 是用户显式敲打指令输入的，而上面的这个 skill 引用的做法依赖 AI 去匹配到这个 skill，如果 skill 的正文没有注入，那么也就不会看到 command.md 的正文了。

常驻成本

其次还有常驻成本，我们已经知道了 skill 能被 AI 匹配而 command 不行的原因是 harness 将 skill 的名单也注入到了上下文，那么这也等同于它就是每个会话的隐性成本，但是因为 command 没有像 skills 那样的名单注入，只在我们调用时才注入，这就省去了这部分的成本。

权限边界

同时还有一个收益，那就是一般像是归档这样的仪式类命令，都会涉及到权限边界，就比如说我很不喜欢 AI 在执行完顺手给我 commit​，或者我只想让他去读而不是改，那么我们就可以通过 frontmatter 里的 allowed-tools​ 去约束它，虽然说我们可以对话嘱咐，但是上下文是会压缩，这句话可能就没了，而且上下文越长，早期的内容存在感就会越低，AI 很可能就忘记还有这玩意了，因此像是不要顺手 commit​ 这种命令写在 agents.md​ 里比较好。至于 command，它是指定仪式的范围，越危险的仪式，就越需要 command 的约束，就比如归档，因为你不可能每次都指望匹配 skill 来解决，而且那种方式也会占用上下文，虽然占据的就是 description 那一点。

总结

目前我认为，command 的编写会比 skills 少很多，但是它确实有好处，像是归档这类活直接让 command 就可以了。当然写在 skill 里也可以，但是这样就会把判断权交给 AI，只有它判断应该这么做的时候才会让 harness 注入 command 的上下文，这是有不确定性的，因此，归档这类活还是由我们自己手动调用 command 比较好。
