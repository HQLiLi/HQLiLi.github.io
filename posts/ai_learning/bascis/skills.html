2026/08/30AI学习

2026.8.30 15:19

‍

早上我在 Zcode 中领到了 GLM5.3-flash​ 3 亿的 token，决定在里面把原先 Trellis 管理的每个规则层给自己搞清楚到底是怎么运行的，先从 Skill 开始。

‍

我让 AI 参考 Trellis​ 的 trellis-brainstorm​ skill 写了一份全局的 brainstorm skill，分别实验了一下，得出了结论：

  1. 如果有开启 skill，AI 在回复前能够在深度思考中看到它使用的 skill 的名称。

  2. skill 的自然语言选择不需要考虑是否用中文还是英文，只需要让自己看得懂就行。

  3. 会话会加载的 skill 只有在点击会话的时候已启用的 skill，如果有 skill 是在会话开启后启用的，当前会话是不会知道的，必须要重开个会话。

  4. 根据 AI 的回答，绝大多数时候是会携带上已启用的 skill，但如果没有带上可以用 / 来指定 skill。

  5. 项目级 skill 的创建方式，有一个约定俗成的规则，就是在根目录下创建 .agents/skills，然后再下面创建 skill 包，举个例子：

    .agents/skills/
└── test-skill/ 包名要与 SKILL.md 里的 name 一致
    └── SKILL.md 固定名称

  6. skill 文件中的头信息一定要有以下的内容：

    ---
name: 名字（这里要跟外面的包名一致）
description: 描述信息
---

‍

skill 的描述决定了 AI 是否调用。AI 在最开始就能知道所有启用的 skill 的名称和描述，它在执行中根据描述来选择该调用的 skill 列表。

那么现在我将所有信息整理一下就是：

‍

AI 在会话开始时会注入 skill 名单（包含 name​ 和 description​），之后就一直停留在上下文中，这也是为什么在会话开始后，我们去新增或者停用某个 skill，AI 却不知道的原因。而在 AI 根据 description​ 来命中 skill 时，该 skill 的正文就会被加载进上下文，而正文指向的附属文件（references 之类的）是按需读取。

这里说一下为什么附属文件是按需读取，以我自己让 AI 写的思源笔记整理 skill 为例，它的正文里有下面的这一段文本：

‍

思源笔记环境：先读参考文件再动手
如果本任务在思源笔记的 AI 对话中执行、需要调用 block 类写操作（insert / append / update / delete / move），
必须先读 references/siyuan-blocks.md——里面有快照密钥、空块创建、反死循环保护三个已知坑的规避方法。
跳过它最坏的后果是对话被平台强制中断。在普通文件系统上整理 .md 文件时无需读它。

‍

在这段内容前面我是加了个关键词 思源笔记环境​ 来修饰，这样的话，如果这个 skill​ 它在其他环境，比如说 vscode 里调用了，因为它不匹配 思源环境​，它就不会去将 references​ 包下的 siyuan-blocks.md 的内容注入到上下文。

这里还要补充一点信息，skill 的名单信息它是处在上下文的稳定区，并不会因为上下文压缩而丢失，它是 harness 在每轮会话都会重新发放一次，这也就是常驻的意思，是每轮重发。

‍

2026.9.6 23:22

skill​ 的触发没有我想象得靠谱，今天我让 AI 写了个页面初稿，然后生成 prd 文档，根据初稿在项目中生成代码，结果 AI 用 vue3​ 写了一堆组件，这从逻辑上来说，既然碰了 vue3，那么应该会触发项目级 skill​ —— vue3-best-practices​，但是 AI 判断并不需要注入它，理由是它直接根据 prd 文档开始执行，因此没有考虑到应该再去判断一下是否有相关的 skill 需要注入，而文档中也并没有提及到要用这个 skill。

解决方法也比较简单，往 AGENTS.md​ 中添加点规则就行，或者用规则层框架（我打算用 Trellis）中的规范文档中添加规范来约束。

‍

2026.11.25

经过几个月的实践，我认为现在其实没有什么必要引入特别多的skill，目前项目中用的绝大多数skill都是跟工作流相关的必须显式调用的skill。像是之前提到的​vue3-best-practices其实反而没必要，因为大模型在训练时已经用了社区主流的编码习惯相关的素材了，它不需要在引入这些已经知道的内容。对于这些内容规范类skill我现在都已经不用
